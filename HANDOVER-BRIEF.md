# Brief: client editing screen + clean handover

Second brief, for after the animation work in `ANIMATION-BRIEF.md` is done.

**Goal:** the Hynson Roofing owner can change their own website text, photos,
projects and reviews without touching code and without ringing the developer.
Then the whole thing gets handed over so the developer is genuinely finished.

Same client notes apply: he is non-technical, explain in plain language, show
visible progress, never leave the site broken.

---

## PART 0 — Must fix before any handover

### 0.1 The contact form is dead

`src/components/Contact.jsx` and `src/pages/Admin.jsx` call
`${REACT_APP_BACKEND_URL}/api/...`. That backend was hosted by Emergent and did
**not** survive the migration. Right now a quote request goes nowhere.

**A roofing site that silently swallows enquiries is worse than no site.** Fix first.

Suggested: Netlify Functions.
- `netlify/functions/enquiry.js` — accepts the form POST, stores to Netlify Blobs,
  and emails the business. Honeypot field for spam.
- `netlify/functions/enquiries.js` — returns stored enquiries for the admin page,
  behind a bearer token from an `ADMIN_SECRET` env var.
- Point `REACT_APP_BACKEND_URL` at the site's own domain, or rewrite the two
  components to call `/.netlify/functions/...` directly.
- Add a `netlify.toml` with the build command, publish dir `build`, and an SPA
  redirect (`/* -> /index.html`, 200) so `/admin` doesn't 404 on refresh.

**Test it end to end.** Submit a real enquiry, confirm the email arrives, confirm it
shows in the admin page. Do not mark this done off the code alone.

### 0.2 Audit the content for invented claims

This site was originally generated by an AI builder. Those tools routinely produce
**placeholder testimonials, fake customer names and invented project histories.**

Read every entry in `src/data/content.js` — `TESTIMONIALS`, `PROJECTS`, `FAQS`, any
stats or "years in business" claims — and produce a list for the client to confirm
line by line.

Publishing invented customer reviews on a live New Zealand business site is the
**business owner's** legal exposure under the Fair Trading Act, not just an
embarrassment. Flag anything unverified clearly and let the client decide. Do not
quietly leave it in.

## PART 1 — The editing screen

### What the client should get

A page at `/admin` (or `/cms`) where the owner logs in and edits:

- All headline and body text on the homepage
- The services list
- The projects gallery — including uploading new job photos
- Reviews / testimonials
- FAQs
- Phone number, email, service areas

Save, and the site rebuilds and updates itself within a couple of minutes.

### Suggested approach: Decap CMS

Free, open source, stores content as files in the repo, no database, no monthly cost.

**The prerequisite refactor:** content currently lives in `src/data/content.js`, a
JavaScript module. A CMS cannot safely edit JS. Convert the data to
`src/data/content.json` and import it (`import content from "./content.json"`),
keeping the existing named exports as re-exports so **no other component has to change**:

```js
// src/data/content.js
import data from "./content.json";
export const CHAPTERS = data.chapters;
export const PROJECTS = data.projects;
// ...etc — keep every existing export name identical
export const API_URL = `${process.env.REACT_APP_BACKEND_URL}/api`;
```

Verify every consumer still builds before going further.

Then add `public/admin/index.html` and `public/admin/config.yml` describing the
editable fields, with an image upload folder at `public/img/`.

**Authentication — verify current options before committing.** Historically this used
Netlify Identity + Git Gateway (one click, no OAuth server). Netlify has been steering
people away from Identity, so **check whether it is still available for new sites in
2026.** If it is not, options are:
- Decap with the GitHub backend plus a small OAuth proxy function
- A maintained fork such as Sveltia CMS, which works with GitHub directly
- A hosted CMS with a free tier

Pick based on what actually works today, not what the old tutorials say. Whatever you
choose, the owner must be able to log in with **one** username and password.

### Non-negotiables for this to be worth doing

- Logging in and changing a headline must take under a minute, with no jargon on screen
- Field labels must be plain English — "Phone number shown in the header", not "phone_primary"
- Image upload must resize/compress automatically. The owner will upload 8 MB phone photos
- It must be usable on a phone
- If a save fails, it must say so clearly rather than silently losing the text

### Write them a one-page guide

Plain language, screenshots, in the repo as `HOW-TO-EDIT-YOUR-SITE.md` and also as a PDF:
how to log in, how to change text, how to add a project photo, how long changes take
to appear, and who to contact if something breaks.

## PART 2 — Account ownership checklist

The developer wants a genuine one-time handoff. That only works if **every account is
in the business's name with the business's recovery details.** Work through this list
and tick every line.

| Account | Must be | Watch out for |
|---|---|---|
| Google/Gmail | New account in the business's name | Create it fresh — never reuse a personal account |
| GitHub | Created with that business email | |
| Netlify | Created with that business email | |
| Domain (Crazy Domains or wherever) | **In the business's name, on the business's card** | The client chose full transfer — do it properly, not just "I'll keep paying it" |
| Email forwarding for enquiries | Goes to an address the business actually reads | |
| Admin/CMS login | Business owns it | Force a password change on handover |

**The two that quietly keep a developer on the hook forever:**

1. **Recovery phone and backup email on the Google account.** If the developer's number
   is on there, he is their password reset service for life. Change these to the owner's
   before handing over, and confirm the owner can actually receive a code.
2. **The domain.** If it renews on the developer's card, he gets a call every year and
   the business doesn't truly own its own address.

Also: remove the developer's own personal devices/sessions from the Google account after
handover, and confirm two-factor is set up on the owner's phone, not the developer's.

## PART 3 — The handover document

Produce a clean one-pager for the client covering:

- The live web address
- What the site does — pages, contact form, where enquiries arrive
- **Ongoing costs**: hosting free at this size; domain renews annually (state the date
  and the amount); any CMS cost
- How to edit the site — pointing at the guide from Part 1
- Where the code lives, and that they own it
- What is *not* included going forward — be explicit and honest about the boundary
- Who to contact for what

**Keep credentials out of this document.** Passwords go in a separate handover sheet,
delivered directly, and the owner is told to change them immediately.

Set expectations honestly. Do not promise ongoing support that isn't being offered, and
do not imply capabilities that can't be delivered in six months' time.
